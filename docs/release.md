# Release and deployment

## 1. Deploy the API on Render

1. Push the repository to GitHub.
2. In Render: **New > Blueprint**, pick the repository. `render.yaml` creates `luma-api` (Go, `rootDir: api`, health check `/health`).
3. Enter the secrets when asked: `OPENAI_API_KEY`, `YARNGPT_API_KEY` and, optionally, `LUMA_CLIENT_TOKEN`.
4. Check `https://<service>.onrender.com/health` and `/v1/capabilities`. Each language should show the features you expect. If one says `no_voice_for_language`, set `YARNGPT_VOICE_<LANG>` to a voice from YarnGPT's `GET /api/v1/voices`.

Free Render instances sleep after inactivity and take about a minute to wake. The app tolerates this (it times out and offers a retry), but use a paid instance for the pilot.

## 2. Build the installable APK

### With EAS (recommended)

The app is linked to the EAS project **`@devquat/luma`**: `owner` and `extra.eas.projectId` are set in `mobile/app.config.ts`. `eas init` cannot write to a dynamic config, which is why they are set by hand.

```sh
cd mobile
npx eas-cli login
# Online features (leave out to build an offline-only APK):
npx eas-cli env:create --environment preview --name EXPO_PUBLIC_LUMA_API_URL --value https://<service>.onrender.com --visibility plaintext
# only if the API requires it:
npx eas-cli env:create --environment preview --name EXPO_PUBLIC_LUMA_CLIENT_TOKEN --value <token> --visibility plaintext
npx eas-cli build -p android --profile preview
```

The `preview` profile produces an `.apk` (`android.buildType: "apk"`, internal distribution) for `armeabi-v7a` and `arm64-v8a`. EAS created the signing keystore on the first build and keeps it, so later builds update the installed app in place.

Two gotchas:

- **No git commits yet?** EAS packages the project from git by default. Until the repository has a commit, prefix the build command with `EAS_NO_VCS=1`. EAS then uploads `mobile/` minus the patterns in `mobile/.easignore`.
- **Delete any local `mobile/android` folder before an EAS build.** If it exists, EAS treats the app as a bare project and skips prebuild on its servers. The folder is generated by `expo prebuild` and is safe to delete.

### Locally (Windows, macOS or Linux)

```sh
cd mobile
LUMA_BUILD_ARCHS=armeabi-v7a,arm64-v8a npx expo prebuild -p android --clean
cd android
EXPO_PUBLIC_LUMA_API_URL=https://<service>.onrender.com ./gradlew assembleRelease
# APK: android/app/build/outputs/apk/release/app-release.apk
```

- **Windows: object paths longer than 260 characters.** React Native 0.88 compiles C++ codegen for several libraries. The object-file paths CMake generates exceed 260 characters even from a very short folder. Measured from `C:\lb\mobile`: gesture-handler 322, safe-area-context 307, reanimated 291, screens 279, svg 263. The Android SDK's default CMake 3.22.1 ships **ninja 1.10.2**, which cannot handle those paths and fails with `Filename longer than 260 characters`. A `subst` drive alias does not help, because the tools resolve it back to the real path. To build locally on Windows:
  1. Turn on long paths (once, as administrator): `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled = 1`.
  2. In Android Studio, open **SDK Manager > SDK Tools**, tick **Show Package Details**, and install a newer **CMake** (3.31 or later). Check that `Sdk\cmake\<version>\bin\ninja.exe --version` prints **1.12 or newer**, the first ninja release that supports long Windows paths.
  3. Add `cmake.dir=C\:\\Users\\<you>\\AppData\\Local\\Android\\Sdk\\cmake\\<version>` to `mobile/android/local.properties`, delete `mobile/android/app/.cxx`, and build again.

  EAS builds run on Linux and are not affected.
- A local release build is signed with the debug keystore from the Expo template. That is fine for testing, but every pilot phone should get EAS-signed builds so updates install over each other.
- For emulator testing against a local API, build with `LUMA_BUILD_ARCHS=x86_64`, `LUMA_ALLOW_CLEARTEXT=1` and `EXPO_PUBLIC_LUMA_API_URL=http://10.0.2.2:8080`. Never ship a cleartext build.

### Before sharing an APK

1. Install it on a real phone. Turn on airplane mode **before first launch** and scan a page. The bundled ML Kit model must work with no network.
2. Run the checks in [verification.md](verification.md) and record the results there.
3. Compute the checksum: `sha256sum app-release.apk` (or `certutil -hashfile app-release.apk SHA256` on Windows).

## 3. Publish the website

```sh
cd web
npm run build          # static site in web/out/
```

Host `web/out/` on any static host (Render static site with publish directory `web/out`, Netlify, GitHub Pages).

To offer the APK, upload it (for example as a GitHub Release asset) and fill in `web/src/content/release.json`: `available: true`, `version`, `url`, `fileName`, `sizeBytes`, `sha256`, `publishedOn`, `testedOn`. The download button appears only when all of these are present. Do the same in `demo.json` for a captioned demo video (`video`, `captions` as WebVTT, `transcript`). Rebuild after each change.

Approved voice samples come from `mobile/assets/prompts/approved.json` entries marked `"website": true`. Run `npm run prompts:sync` in `mobile/`, then rebuild the website.
